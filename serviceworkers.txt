Service Worker Implementation – Questions & Context
--------------------------------------------------

Goal:
Create a service-worker that intercepts requests for the web-app (especially on `/` and `/app`) and caches `.json` and `.webp` responses. Images are requested via plain `<img>` tags, so the worker will need to handle runtime caching (not precaching) for those requests.

Outstanding Questions for the User
---------------------------------
1. Build / Deployment
   • What build tooling is the app using (e.g. Vite, Create-React-App, Next.js, plain HTML)?
   • Is an existing service-worker already generated by the build system that we must replace or extend?

2. Scope & Routes
   • "All requests to / and /app" – does this refer only to the HTML documents at those paths, or *any* network request whose pathname starts with `/` or `/app`?
   • Should the service-worker be registered at the site root so it controls every sub-route, or only inside `/app`?

3. Resources to Cache
   • Besides `*.json` and `*.webp`, should other static assets (JS, CSS, fonts, etc.) be precached or runtime-cached?
   • Are the images / JSON fetched solely from the same origin, or do they come from external domains as well?

4. Caching Strategy
   • Images: cache-first vs stale-while-revalidate?
   • JSON: network-first with cache fallback vs another strategy?

5. Cache Invalidation / Limits
   • Any TTL (time-to-live) or maximum entry count desired (e.g. last 200 images, 7-day max age)?
   • Should a newly activated service-worker purge all old caches automatically?

6. Offline Behaviour
   • Is an offline fallback page or placeholder image required when both network and cache miss?

7. Libraries / Implementation Style
   • Is it acceptable to use Workbox (adds a small runtime library) or must we write a vanilla service-worker?

Context Saved for Future Work
-----------------------------
• Current project already contains a Cloudflare *worker* at `worker/worker.ts` (server-side edge worker) – unrelated to a client-side service-worker.
• No service-worker files exist yet in `src/` or `public/`.
• User's primary requirement: cache `.json` and `.webp` responses for `/` and `/app` routes to improve load times.
• Registration script will eventually need to be added to the React app (likely in `src/index.tsx` or similar).

When the above questions are answered, we can design:
1. Registration code (e.g. `navigator.serviceWorker.register('/sw.js')`).
2. Service-worker file (`public/sw.js` or similar) implementing chosen caching strategies.
3. Build-tool integration (copy / inject worker, Workbox config if used).
